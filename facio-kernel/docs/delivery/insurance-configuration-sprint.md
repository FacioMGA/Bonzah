## Implemented increment and evidence boundary

The working tree adds structured product authoring in the existing Studio, canonical active-product evaluation and operator quote capture/bind. The single authoring home is `configuration.products[].insurance`; typed operating policies retain currency, effective window, commission, participant caps and prerequisite gates. Saving changes the existing configuration draft, and activation freezes both inside the existing immutable sandbox release. No second store or browser decision engine is introduced.

Implemented authoring supports text, single choice, boolean, safe integer, exact decimal, money and date questions; requiredness and scalar bounds; country applicability; explicitly chosen minimum/maximum term and backdating policy; coverage selection, dependencies and exclusions; fixed limit/deductible ranges; flat, per-unit and selected-limit percentage rates; all/any typed comparison, membership and presence predicates; referral/decline rules, rating factors, minimum premium and numeric authority thresholds. Source references are declared unverified claims. Money uses exact string scaling in the UI and canonical server arithmetic.

Every coverage must explicitly declare `basis: single_risk_per_occurrence`. Its limit and deductible are fixed currency amounts for a single risk per occurrence. The authority threshold sums these comparable selected limits as a conservative configuration check; it is not a policy aggregate, claims maximum, per-person allowance or excess attachment calculation. Other bases are rejected by the strict schema. Runtime policy currency must equal the configuration tenant currency at activation, and rich evaluation resolves only an immutable managed release. Term duration counts inclusive UTC calendar days; backdated starts are either prohibited or require an unsupported approval gate. None of these values are copied from customer examples or silently defaulted.

Preview is active-definition-only, through the canonical service exposed to Studio/API/MCP. It creates no insurance record. Configured quote capture re-evaluates the exact input and expected hash; bind checks the retained release and current prerequisites. The backend contains configured quote revision, but **the Studio revision UI is deferred and disabled**. Rich-policy endorsement, cancellation and reinstatement are blocked pending risk-aware servicing; the retained manual external-quote path remains available for its separately configured products.

The integration owner's first local HTTPS browser run passed structured authoring without JSON, invalid and referred risk previews, identical UI/API decision hashes, quote capture and binding against the original release after a later price activation, cross-tenant denial, and desktop/390px decision rendering without page errors or horizontal overflow. The reproducible harness is [insurance-configuration-browser-smoke.ts](../../scripts/insurance-configuration-browser-smoke.ts); its ignored output is `test-results/insurance-configuration-browser.json`. That initial run preceded the explicit term/basis additions, whose rerun remains required. Component-only checks separately preserved money and monetary predicates beyond the JavaScript safe-integer range and blocked read-only save. These are synthetic local checks, not external identity, hosted deployment, full IC-01–17 or customer golden acceptance. The authoring mobile screenshot initially retained the open navigation drawer and needs a closed-drawer recapture for readable visual evidence.

Deferred capabilities include repeated risks/locations and row quantifiers, conditional question visibility/requiredness, field-level evidence review, computed questions, multilingual questionnaires, aggregate/per-person/percentage or layered terms, sublimits/wording execution, tax/fee and proration engines, human approval resolution, authenticated providers and callbacks, draft simulation, and full customer lifecycle/document/financial behavior. Unsupported schema inputs fail validation; a complete typed `REQUIRES_ENGINEERING` diagnosis for every future feature is still a requirement, not implied by strict schema rejection.

## Agreed integration boundary and wider target invariants

The canonical operations use these boundaries:

- Optional `configuration.products[].insurance` is the single authoring home; rich products require `fields: []`.
- `insurance_evaluate_product`, `POST /api/insurance/evaluate`, accepts product ID/version and a typed submission (answers, territory, term, selected coverage limits/deductibles, source reference/version/evidence and expiry). It returns separate validation, applicability, eligibility, referral, rating, authority, approval and bind evidence plus pinned hashes.
- `insurance_create_configured_quote` re-evaluates and compares `expectedEvaluationHash`, then stores canonical input/evaluation and derives the premium on the server. It does not accept a client eligibility outcome or price as authority.
- Bind re-evaluates against the original pinned historical definition. Existing manual records are preserved. Rich-product servicing fails closed until risk-aware servicing exists.
- The bounded evaluator supports scalar fields, coverage requirement/dependency/exclusion/limit/deductible checks, flat/per-unit/limit-basis-point rating and explicit factors with exact rounding, with pricingOwnership: kernel_deterministic. Typed all/any conditions have true/false/unknown semantics. Both decline and referral evidence survive; missing data never becomes automatically eligible. Approval remains `required_unsupported`.

## Risk questionnaire: field semantics

The following table specifies the complete target semantics. The initial implementation is limited to the scalar types and behavior listed above; repeatable objects, conditional questions and field-level discrepancy resolution are not implemented.

Each question needs a stable ID, risk-object scope, section/order, business label, help text, answer type, unit/currency where relevant, validation constraints, requiredness, source/evidence requirements and an explicit supported visibility condition. Labels may change without repurposing an existing field ID. Currency, scale and units are part of the contract, not presentation guesses.

| Type / concept         | Required behavior                                                                                            | Examples and boundaries                                                                                                                     |
| ---------------------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Text                   | Trim only according to declared normalization; length limit; preserve submitted text in provenance           | External risk reference, vehicle model or construction narrative; do not infer a jurisdiction from a free-text address                      |
| Integer                | Canonical integer within declared inclusive bounds; no floating coercion                                     | Driver age, building year or rental duration. Date-derived age/duration must use an explicit supported calculation and as-of rule           |
| Decimal quantity       | Exact decimal string with declared scale/unit and inclusive bounds; no rounding during parsing               | Floor area in square metres, not a monetary amount; converting square feet is a separate explicit transform                                 |
| Money                  | Canonical currency and exact minor-unit string; business UI shows decimal currency amount                    | Building sum insured, contents value, coverage limit or deductible. Unknown tax/value is not zero                                           |
| Boolean                | True/false distinct from missing; optional unknown status if the definition permits it                       | Valid licence declaration, vacant building; unchecked UI must not silently mean a negative answer                                           |
| Enum / multiple choice | Stable codes with labels; reject unknown or duplicate codes                                                  | Construction class, occupancy, vehicle class. Option text is not the stored code                                                            |
| Date / period          | Real calendar dates; explicit inclusive/exclusive end semantics and relevant time zone                       | Property policy term and rental return time are different concepts. A four-day rental cannot be derived from ambiguous date arithmetic      |
| Country / subdivision  | Explicit normalized codes and named meaning                                                                  | Residence, risk location and pickup state remain separate. Neither EU data residency nor entity territory proves underwriting authorization |
| Repeatable object      | Stable row ID, min/max count, typed child fields and explicit rule quantifier                                | Named drivers or property locations; one institutional record may have many premises/SOV rows. Array position is not identity               |
| Evidence / discrepancy | Source record/version + locator; submitted value, observation and reviewed resolution retained independently | Missing document, uncertain provider match, competing SOV totals; resolution needs authorized actor, old/new value, reason and time         |

For the initial scalar increment, support only types/conditions that the runtime actually validates. Repeated risks, calculations, multilingual labels and evidence collection remain visible requirements if not implemented. They must not be exposed as configurable options that merely save JSON. A quoted product requiring an unsupported repeated object is blocked rather than flattened into a summary.

Conditional visibility and requiredness use a bounded typed predicate vocabulary, such as equality, set membership, numeric range and the supported all/any structure. Any additional operator must be explicitly supported by the strict schema. Require type-compatible operands; reject unresolved field IDs, cycles and excessive expression depth. Missing/unknown values produce an explicit incomplete result, not false-by-coercion. Hidden stale answers must not affect rating: normalize according to an explicit retained answer policy, expose excluded values in the trace, and reject attempts to activate an undefined policy. No free-form JavaScript, SQL or arbitrary expression evaluation is accepted.

## Coverage terms: operational meaning

This table describes the wider requirement union. The current executable contract supports only explicit single-risk, per-occurrence fixed currency ranges, required/optional selection, dependencies/exclusions and the stated pricing methods. It does not implement every basis, layering model or lifecycle behavior below.

| Coverage element                | Authoring requirement                                                                                                      | Execution/validation                                                                                                                                                                         |
| ------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Identity and scope              | Stable coverage ID, display name, covered risk object/peril, wording/version references                                    | Reject selected unknown/inactive coverage; retain exact wording ref for later documents                                                                                                      |
| Selection state                 | Included, optional or unavailable, with effective dates and selection reason                                               | Required included covers cannot be removed; unavailable cover cannot be selected even through API                                                                                            |
| Limit                           | Money with currency, basis and allowed fixed/options/range value; e.g. per occurrence, per person, per location, aggregate | Validate chosen value against the exact basis and currency. | Deductible / excess             | Fixed amount, or supported percentage with explicit base and minimum/maximum; basis and application scope                  | Validate independently from premium. | Sublimit                        | Stable child ID; parent coverage/limit; peril or property scope; amount/basis                                              | Validate relationship only where comparable basis/currency makes the comparison valid; otherwise demand an explicit rule                                                                     |

Treat excess attachment and primary coverage as distinct from a deductible. Preserve loss occurrence versus claims-made wording as a defined product fact when supplied; do not infer a trigger from customer sector or coverage name. Full claims adjudication is outside this slice. These semantics are configuration requirements, not statements that a particular customer's contract has been approved.

## Decision order and action readiness

Expose separate results, for example `validation: valid|invalid|incomplete`, `eligibility: eligible|declined|undetermined`, `underwriting: clear|referred|blocked|undetermined`, `rating: not_requested|available|failed|unverified`, with action gates containing `allowed|blocked|unsupported` and reasons. Final enum names are subject to the implementation contract; the separation is mandatory.

1. **Authorization and version selection:** resolve explicit target/actor on the server, choose the retained definition and check supported schema/effective window. Invalid scope or incompatible definition terminates the command before business work.
2. **Input/coverage validation:** validate types, conditions, required evidence, selected cover dependencies and term meaning. Malformed/incomplete input returns actionable field/rule errors. It must not be classified as an underwriting decline.
3. **Jurisdiction and eligibility:** apply explicit product eligibility rules to the declared pickup/risk/residence field, coverage and transaction type. No matching required jurisdiction rule means undetermined/block, never global permission.
4. **Underwriting/referral:** evaluate risk signals and unresolved discrepancies; preserve all matched reasons in stable rule-ID order. A decline dominates a referral for final quote permission, and an unresolved referral blocks bind even if an external premium exists. Keep the separate underlying results visible.
5. **Rating:** only invoke a configured compatible pricing source for an input state that permits it. A referred risk may display a clearly provisional external indication if the selected contract permits that behavior, but may not become bindable. Provider failure is a technical unavailable result, not a zero price or risk decline.
6. **Quote, bind and issue prerequisites:** independently enforce configured authority, screening, subjectivities, documents, payment/receivable evidence and expiry. Their exact customer order remains a decision input. Missing/unsupported mandatory capabilities fail closed. A clear risk or accepted external price is insufficient to authorize bind/issue.

Warnings and cross-sell recommendations do not change eligibility. Match all applicable rules and retain explanations rather than silently using whichever rule appears first. Rule precedence, comparison precision, effective-date semantics and missing-value behavior must be versioned and tested. No claim of automated referral resolution is allowed until the separate authority-controlled approval command is implemented.

### Jurisdiction and authority are different contracts

Jurisdiction settings need the interpreted field (`pickupSubdivision`, `riskLocation`, `residence`, etc.), allowed codes, effective window, coverage scope and explicit result/reason. They do not constitute a legal licence or a capacity agreement. Authority requires a separately identified agreement/version, applicable entity/product/territory/transaction, approved limits and conditions, current actor authority and evidence. Premium caps, insured limits, total insured values, signed participation and carrier authority are separate measures and cannot share an unexplained number field.

Initial implementation should retain current `required_unsupported` authority/payment/provider gates where those capabilities do not execute. An author can configure a clearly synthetic no-prerequisite manual policy for testing, but cannot turn a customer-required approval into `not_required` merely to clear a gap. The reviewed customer package and acceptance case must retain that unresolved requirement.

## Rating and external provider boundaries

**K03 configured path:** evaluate the selected product.insurance definition and supported exact tariff, then create a quote only when a server re-evaluation matches expectedEvaluationHash. Flat, per-unit and limit-basis-point calculations have explicit units, factors and rounding; the client cannot supply the resulting premium or eligibility. Retain the existing manual external-quote path and historical records separately. Neither path is authenticated QuoteBox integration.

**K04 next path:** a registered adapter accepts the approved external contract, preserving request/response version, exact source risk/quote identity, outcome reasons, field mapping and evidence. Authenticated ingress, request-signature/credential checks, inbox deduplication, command idempotency, ordering, atomic state/events/audit, and recoverable outbound delivery belong to canonical services. A callback receipt cannot update a different target, downgrade newer quote evidence or duplicate business money.

| Adapter result                       | Canonical behavior                                                                                                |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| Accepted quote                       | Preserve provider input/output and exact priced coverage/terms; create one immutable version with source identity |
| Referred / declined                  | Record the external result and reasons separately from local eligibility/authority; no bind                       |
| Timeout / unavailable                | Persist attempted operation and retry disposition; no apparently valid quote or fabricated output                 |
| Duplicate source event               | Return recorded stable outcome; never create another quote/bind/allocation                                        |
| Late/superseded version              | Retain evidence or reject according to declared contract; never silently replace the selected version             |
| Unknown or ambiguous screening match | Explicit referral/evidence requirement; not a clear result                                                        |
| Unmatched/malformed fields           | Structured mapping/validation failure, source locator retained; no partial accepted record                        |

The provider connection is a server-managed reference; models and browser forms never receive credentials. State whether an adapter is implemented, configured, reachable, authenticated and actually exercised as separate facts. Any simulated processor/engine must be an explicit synthetic boundary selected for that scenario.

For the selected bounded internal tariff modes, implement versioned coverage-level components, unit/period basis, explicit factors, rounding and complete golden examples. Minimum premiums or additional algorithms may be configured only if the strict schema and evaluator implement them. Taxes, fees, commercial markup, brokerage, commission and technical premium remain distinct. Unknown charge ownership cannot default to a zero-tax total. This narrower algorithm cannot be labeled the complete PRD-006 formula/table/override capability.
