M3 · Configuration visibility
Deadline: Tuesday, 8 September 2026. This is the earliest gate and an enabling dependency for M1, M2 and M4.
Deliverable | Acceptance requirement
API Documentation screen | Authenticated users can discover configuration categories, inspect current values and distinguish drafts from published/effective versions, within their tenant and role scope.
OpenAPI | A retrievable, valid specification documents implemented configuration endpoints, schemas, required/conditional fields, enums, validation errors, authentication and supported operations.
MCP | Authorised clients can discover configuration tools and inspect the same configuration model and completeness report. Writes delegate to canonical services and respect draft/publication permissions.
Gap inventory | List missing, incomplete, invalid, inconsistent and unsupported configuration. Each row identifies tenant/product/process, field or capability, applicable requirement, current state, expected state, affected journey, severity and remediation.
Cross-surface parity | One representative complete tenant and one deliberately incomplete tenant return consistent results in the screen, OpenAPI-backed API and MCP. Secrets are represented as connection status/references, never plaintext.
Evidence: screen walkthrough, OpenAPI artifact, MCP discovery/read output, completeness report and tenant-isolation checks. A documentation page describing unimplemented endpoints does not meet this gate.
M1 · Bonzah and UE demo readiness
Deadline: Thursday, 10 September 2026, before the demo. Internal target: full rehearsal and candidate configuration freeze on Wednesday, 9 September.
Baseline and trace every approved Bonzah and UE demo requirement to a runnable journey, configuration entry and acceptance test.
Provision separate demo tenants using the same Kernel build and their own configuration, approved sample data, documents and integration profiles.
Exercise each agreed journey end to end, including outputs and any configured referral, approval or failure path required by the scenario.
Demonstrate a material tenant behaviour change through configuration without editing shared runtime code.
Review changes for tenant-name branches, embedded customer rates/rules, duplicated lifecycle logic and customer-specific database access. A reusable typed extension is acceptable only with an explicit capability contract and configuration-based registration.
Record build and configuration versions, rehearsal evidence, reset procedure and an issue list. No unresolved issue may block an agreed demo journey.
If any external provider is simulated, label it explicitly and obtain acceptance of that demo boundary; preserve the real integration contract.
M2 · VUW.ai full POC acceptance
Deadline: Friday, 11 September 2026. Internal target: complete integrated POC run on Thursday, 10 September, with Friday reserved for acceptance and fixes.
Scope boundary. The complete agreed VUW.ai POC is the acceptance baseline. Submission, quote and underwriting are known context, but cannot substitute for the full source scope. The exact POC document and version must be attached to the delivery tracker on 7 September.
Run VUW.ai as an isolated tenant on the shared Kernel with its approved product, process, authority, document, reporting and integration configuration wherever required by the POC.
Maintain a scope matrix: source requirement → configured capability → test scenario → expected output → result → evidence → defect.
Pass every mandatory POC requirement, including interfaces and outputs. Make environment limitations explicit and agree any third-party test boundaries before execution.
Confirm lifecycle persistence, authorised role behaviour, tenant isolation and repeatable results for the agreed scenarios.
Deliver the completed scope matrix, walkthrough, build/configuration references and acceptance record. Any failed mandatory item means the full-POC milestone remains incomplete.
M4 · End-to-end self-onboarding specification
Deadline: Saturday, 12 September 2026. Deliverable: an experience and interface specification ready for engineering breakdown. This milestone does not require implementing the entire onboarding service.
Experience area | Required specification
Website entry and identity | Entry points, sign-up/login, verification, organisation creation, invitations, role selection and resume-on-return.
Plan, subscription and billing | Plan comparison/selection, entitlements, trial if offered, payment setup, invoices, tax details, renewal, upgrades/downgrades, cancellation and failed-payment recovery.
Configuration journey | Business/product/process intake through forms or LLM/MCP; source upload, validation, missing-information guidance, progress and saved drafts.
Environment and domain | Residency selection, provisioning status, default URL, customer domain ownership verification, DNS/TLS states, errors and retry.
Draft/test → Live | Test data isolation, simulation, readiness checklist, approval and authority, payment/subscription gates, configuration publish, activation status and rollback/recovery.
Customer account panel | Account/subscription state, profile, organisation/users, billing/invoices/payment methods, environment/domain, service requests, support status and notifications.
M4 · Interface and design handoff
For every screen and material button/action, specify actor, preconditions, fields, validation, command/API, resulting state, permissions, loading/empty/error states and recovery. Include mobile behaviour and accessibility requirements.
For every external interface—identity, Control Plane, Kernel configuration/MCP, payment provider, subscription/entitlements, infrastructure provisioning, domain/DNS/TLS, CRM, support and notifications—document the system of record, payload contract, authentication, webhook/event, idempotency, retry and reconciliation. Specific providers remain decisions until selected.
Acceptance evidence: linked journey map, annotated screens/wireframes, account/subscription/environment state models, API/event interface catalogue, Draft/test-to-Live gate matrix and an exception catalogue. Product, UX and Engineering must be able to trace the journey from website entry to live operation and subsequent account servicing.
