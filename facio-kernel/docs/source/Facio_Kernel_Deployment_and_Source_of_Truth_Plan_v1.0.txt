3. One authoritative source per concern
One source of truth is a governed ownership model. Independent copies must be generated projections or explicitly versioned compatibility contracts, with provenance and a retirement policy.
Concern / owner role | Authoritative source | Consumers / invariant
Domain behaviorKernel Engineering | Owning domain commands, schemas and capability descriptors in the Kernel. | UI, API, MCP, imports and jobs call the same domain paths; no independent transport business logic.
Tenant behaviorProduct / Configuration | Versioned tenant, product, process, jurisdiction, document and integration packages. | Published immutable Tenant Release; draft changes never silently alter live behavior.
Deployment intentPlatform Engineering | Version-controlled infrastructure and per-environment deployment manifests. | Cloud state is observed and compared with desired state. Drift becomes a tracked exception, not a silent overwrite.
Public contractsAPI / MCP Engineering | Canonical schemas plus explicit HTTP and MCP operation descriptors. | Generate OpenAPI, MCP discovery, configuration catalog and documentation models. Share domain definitions without assuming HTTP and MCP are identical.
Commercial recordsCRM / Billing owner | Designated CRM and billing services with stable account/subscription IDs. | Control Plane and website consume governed APIs/events. One writer per commercial fact.
Observed deploymentPlatform Operations | Deployment registry populated from CI/CD and authenticated runtime observation. | Customer support, deployment map and API screen show verified versions and timestamps.
Published documentationDeveloper Experience | Versioned release artifacts and approved explanatory source content. | Website, portal, SDK examples and agent-readable discovery reference the same released contract lineage.
Release manifest — required provenance
Record Kernel commit and image digest; schema/migration version; Tenant Release and compatibility adapter versions; OpenAPI, MCP and configuration-catalog versions and hashes; documentation build and source references; supported capabilities; target tenant/environment/region; publication status; deployment time and validation evidence. Never expose secrets, private infrastructure or another tenant’s configuration in a public manifest.
Ownership and operating rules
Every record, contract and generated artifact has one accountable owner and a named maintainer.
Changes enter through a reviewed source change or configuration publication; generated output is not hand-edited.
Customer-specific contracts may coexist when capabilities differ, but each is an explicit projection or supported compatibility version.
An emergency service fix follows the existing production path, then receives contract, manifest and documentation reconciliation within a tracked incident task.

Retirement procedure
Classify each occurrence as authoritative source, generated output, compatibility shim, supported older version, historical material or unused duplicate. Trace imports, jobs, routes, SDKs, bookmarks and agent discovery before removal. Replace live links and search indexes; remove retired content from active agent discovery. Preserve clearly labeled historical versions only when needed, with canonical replacement links. Do not delete functional re-exports merely because filenames match.
Configuration gap register. For every configuration type and field, publish support state: complete, partial, missing or deprecated; UI/API/MCP coverage; validation and simulation support; owner; affected customers; workaround and target milestone. Unknown must be distinct from unsupported. Show authorized tenant-specific gaps in the API Documentation screen.
5. Continuous documentation delivery
Changes to domain schemas, routes, MCP tools, tenant configuration schemas, adapters or deployment metadata must trigger the following pipeline. Documentation is part of release acceptance.
Gate | Required automated behavior
1 · Validate source | Lint schemas and descriptors; detect breaking changes; verify auth, permissions, tenant isolation and capability metadata. Validate OpenAPI output against its declared specification version.
2 · Generate artifacts | Build OpenAPI, MCP schemas/discovery, configuration catalog and gap report, reference pages, examples and applicable SDK artifacts from the same versioned inputs.
3 · Check parity | Exercise representative exposed HTTP operations and MCP tools against the release; verify required fields, errors, permission denials and configuration visibility. Tenant context must be server-authorized.
4 · Package and deploy | Pin all hashes in the release manifest; deploy through the customer’s governed lane. Keep last-known-good docs until matching runtime availability is verified.
5 · Publish | Update API Documentation screen, developer sites and agent discovery for the deployed tenant/environment/version. Invalidate caches and rebuild search indexes. Preserve explicit supported-version navigation.
6 · Observe and reconcile | After every deployment and on a proposed daily schedule, compare runtime versions, served OpenAPI/MCP hashes, registry and public docs. Open an owned drift issue; never silently promote a mismatched contract.
Publication failure and urgent fixes
Block planned releases with unapproved breaking contracts or failed parity checks. For a necessary production incident fix, use the existing incident authorization path, preserve accurate prior-version documentation, label availability and track urgent reconciliation. A documentation outage must not force a rollback that risks customer data. Keep the new release unpublished as generally available until its supported contract can be served accurately.
Definition of done
For each live tenant and environment, support can identify the running Kernel, configuration and contract versions from one registry record.
API screen, OpenAPI and MCP expose consistent supported configuration capabilities and the same unresolved-gap status.
Website links, downloadable schemas, examples, SDK versions and agent discovery resolve to the intended released contract; retired links are handled explicitly.
A deliberately mismatched contract hash is detected and prevents an ordinary release from being labeled current.
Documentation projections omit secrets and internal-only fields; access control prevents cross-tenant configuration disclosure.
6. Production migration runbooks
Abbeygate — controlled reset into Cyprus
Inventory exact source/target account and tenant IDs, databases, object stores, search indexes, queues, credentials, integrations and CRM mappings. Confirm whether “one Cyprus account” means tenant, operating entity or both. Preserve applicable territory and jurisdiction rules for business still serviced outside Cyprus.
Prepare the Kernel target and compatibility adapters. Prove existing customer journeys, documents, ratings, permissions, reporting and integration behavior using agreed representative cases.
Agree the retained source of operational truth during parallel running and the precise reset scope. Create and restore-test scoped backups/exports. Do not reset shared infrastructure or unrelated customer records.
At cutover, isolate scoped workers and inbound events, establish the final synchronization boundary, apply the approved reset/consolidation and reconcile any records that must remain operationally available. Preserve audit evidence of the reset itself.
Validate Cyprus identity, domains, payment and webhook routing, numbering and customer access. Re-enable one writer and replay only safe, deduplicated events. Rollback must account for post-cutover writes; do not restore an old snapshot over new transactions.
Altus — preserve all production data
Verify the active App Service/Helm lane, exact production data stores and integration endpoints. Capture baseline counts, stable IDs, financial totals per currency and account, attachment checksums, permissions and audit relationships.
Use backward-compatible schema expansion and versioned adapters. Restore-test backups; rehearse migration on an isolated copy with external side effects disabled. Define acceptable cutover interruption and recovery objectives with operations.
Backfill with checkpoints and reconcile. Capture intervening changes through logs or an equivalent reliable delta mechanism. Run shadow reads/comparisons while keeping a single authoritative writer; never duplicate charges or outbound notifications.
At cutover, drain or briefly pause writes if needed, apply the final delta, reconcile all in-scope records and financial/control totals, then switch routing. No lost writes, orphaned records or missing files are acceptable.
Monitor agreed customer journeys and reconciliation reports. Prefer safe forward repair; any rollback must preserve writes made after cutover. Remove legacy schema or storage only after all dependent consumers are retired and retention requirements are met.
Continuity gate. Maintain the active service lane, incident ownership and customer support throughout migration. Urgent fixes must remain deliverable without waiting for all tenants to move. Carry shared fixes into the Kernel lineage and test affected adapters. No big-bang customer rewrite is a prerequisite.
