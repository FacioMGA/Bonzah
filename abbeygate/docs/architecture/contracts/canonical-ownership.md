# Canonical-ownership — binding contract

## Governs
Every domain concept has **exactly one** canonical implementation. Other usages are wrappers, projections, derived UI state, or consumers — never a competing source. Principle from [ADR-0011](../decisions/ADR-0011-policy-state-and-compliance-canonical-placement.md).

## Scope
Payment + checkout + issuance + issue-readiness + the wizard payment step + product rate tables. Extend this file with rows for new domains as they are mapped; do not split into per-domain files.

## Forbidden
- A second implementation of any concept above (per-row "Forbidden duplicate sources" cells are the operative list); hardcoding a product code in shared wizard/UI code (must be parameterised).
- A consumer shadowing what `IProductAdapter` exposes (`backend/modules/policy/domain/productContracts.ts`: `calculatePremium`, `buildQuoteResponse`, `validateForIssuance`, `buildDocViewModel`, `buildVersionRows`, `getEndorsementCatalog`/`getEndorsementTemplate`/`getEndorsementGroups`, `getDefaultClaimsContract`, `normalizeQuoteDataForValidation`, `normalizeUwData`, `calculateEndorsementPremium`) or bypassing it for pricing (`calculatePremium` / `buildQuoteResponse`). Leaf calculators in `backend/products/<product>/pricing/` are reached **only** through the adapter — no `import { calculate*Premium / calculate*QuoteResponse }` outside the per-product engine module; product-string branches forbidden in shared code.
